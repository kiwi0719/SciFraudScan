# False-positive rates on real data

Measuring a false-positive rate normally needs a corpus known to be sound,
which is the hard part — "not retracted" is not the same as "correct".

This sidesteps it. Take **real raw data**, compute the summary statistics
yourself, and round them the way a paper would. The reporting is then correct
by construction, so **every flag is a demonstrable false positive**, with no
assumption about anybody's integrity involved. Real data also brings what
synthetic data cannot: genuine rounding granularity, genuine ties, genuine
correlation between variables.

Source: 300 datasets sampled from
[Rdatasets](https://vincentarelbundock.github.io/Rdatasets/), the example data
shipped with R packages — ordinary teaching and research data with no
connection to research misconduct.

```bash
python benchmarks/false_positives/fetch_datasets.py
python benchmarks/false_positives/measure_validated.py
python benchmarks/false_positives/measure_experimental.py
```

## Validated checks

| Check | Cases | False positives | Rate |
|---|---|---|---|
| GRIM | 2674 | 0 | **0.00%** |
| GRIMMER | 2674 | 0 | **0.00%** |
| Reported p (Student t) | 653 | 0 | **0.00%** |
| Reported p (Mann-Whitney U) | 653 | 0 | **0.00%** |
| Baseline p reachability | 653 | 0 | **0.00%** |

The Mann-Whitney and baseline rows matter most, because they run on real data
with real ties and on p-values computed from raw data but printed beside
rounded summaries — the two situations the one-sided logic was built for.

Getting to zero took two fixes, both found here:

- **Rounding convention.** GRIM compared rounded values using Python's
  `round`, which rounds half to even. At n = 80 a total of 274 gives 3.425 —
  3.42 under that rule, 3.43 under the round-half-away-from-zero that SPSS and
  Excel use. The test now asks whether a candidate total falls inside the
  reported value's rounding interval, accepting both boundaries.
- **Float precision.** GDP figures around 1e13 and an ISBN treated as a
  measurement produced 13 false positives, because a double cannot resolve
  half of the last decimal place at that magnitude. GRIM and GRIMMER now
  report such rows as unevaluable instead of guessing.

## Experimental checks

Not provably false positives — real data can legitimately hold a derived
column or a repeated block — but these are ordinary datasets, so a high rate
means the check is describing something common rather than something wrong.

The first measurement put the rate at 89%. Half the datasets were then used to
diagnose and recalibrate, and the numbers below are measured on the **150 held
out from that work**.

| Check | Before | After | Ran on |
|---|---|---|---|
| Terminal Digit Preference | 87% | **8%** | 88 |
| Benford First Digit | 74% | **0%** | 0 |
| Covariance Structure | 57% | **0%** | 143 |
| Repeated Value Blocks | 70% | 43% | 149 |
| Near Duplicate Rows | 53% | 45% | 127 |
| Carlisle Baseline Balance | 63% | 65% | 57 |
| Repeated Increments | 23% | 22% | 149 |
| Near-Perfect Correlation | 22% | 20% | 149 |
| Over-Regularity | 17% | 21% | 149 |
| Linear Transformation Duplicate | 12% | 10% | 149 |
| Constant Ratio | 11% | 10% | 149 |
| Constant Difference | 9% | 7% | 149 |
| Permutation Duplicate | 7% | 6% | 149 |
| Exact Duplicate Rows | 0% | 0% | 149 |

**At least one experimental flag: 89% → 75% of ordinary datasets.**

### What was fixed, and how

**Terminal digit preference, 87% → 8%.** Two changes. Columns that never show
some terminal digit are recorded more coarsely than their last place, and
every such column in the reference data exceeded the old threshold; they are
now reported as untestable, because "every value ends in 0 or 5" fits a scale
marked in fives exactly as well as rounding by hand and the data cannot say
which. For the rest, the threshold is the 97.5% quantile of real published
columns rather than a theoretical `V >= 0.10`, which 40% of real columns
exceeded.

**Benford, 74% → 0%.** Whether a variable is generated by a multiplicative
process spanning orders of magnitude is a fact about the world, not about the
column, and cannot be inferred. The check now runs only when the caller
asserts it applies.

**Covariance structure, 57% → 0%.** Near-collinear columns and rank-deficient
covariance matrices are ordinary — a total beside its parts, a percentage
beside its count. The check now only ever describes the columns.

**Repeated value blocks, 70% → 43%.** The count is compared against the same
count after shuffling each column, and sorted columns are excluded, since a
sorted column repeats runs for reasons that have nothing to do with
provenance. Both helped; neither was enough.

### What is still broken

**Repeated value blocks (43%) and near duplicate rows (45%) remain useless as
flags.** The permutation null they now use is still the wrong null: real data
carries ordering and grouping structure that shuffling destroys, so the test
answers "is this ordering non-random" when the question is "was this block
copied".

**Carlisle baseline balance (65%) is not measured fairly here.** The harness
hands it the first binary column of each dataset, and these are not
randomized trials, so imbalance is expected. Measuring it properly needs a
corpus of real RCT baseline tables, which this benchmark does not have.

**Terminal digit preference lost sensitivity to get its rate down.** The
heaping planted in `examples/fabricated_trial.csv` sits at the 94th percentile
of real published columns and is no longer flagged. That is the honest finding
and not a tuning failure: real published data heaps on 0 and 5 as hard as that
fabrication does, so no threshold separates them. A targeted test for excess
0/5 specifically, rather than the omnibus chi-square, was tried and separated
no better.
